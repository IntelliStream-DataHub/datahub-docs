# Policies

<Personas>
  <Persona primary>Administrators</Persona>
  <Persona primary>Data stewards</Persona>
  <Persona>Compliance</Persona>
</Personas>

<KeyIdea>
A **policy** is a rule the platform holds and enforces on your behalf: what an identifier must
look like, what a kind of thing must carry, and how long data may be changed and kept.

Three kinds act today. A **naming** policy checks every new external id. A **schema** policy
says what a node of one type must or should have, and refuses or flags a write that breaks
it. A **lifecycle** policy freezes data after an age and deletes it after a longer one.

Attached to no data set, a policy covers the whole tenant; attached to data sets, it covers
them and every data set below them.
</KeyIdea>

## The kinds

| Kind | What it decides | What happens |
| --- | --- | --- |
| **Naming** | What an [external id](/concepts/naming-and-standards#external-ids-are-promises) must look like: a preset, or a pattern of your own | A write that breaks it is refused, or accepted with a finding |
| **Schema** | What a node of one type, optionally with certain labels, must or should carry: a metadata key, a field, a relationship | A **Must** rule refuses the write; a **Should** rule accepts it and records a finding |
| **Lifecycle** | When data stops being editable, and when it is deleted | Frozen data cannot be changed or deleted; a nightly sweep deletes what is past its retention |
| **Legacy** | Lifecycle, access and requirement drafts saved before policies were enforced | <span className="t-accent">Nothing.</span> Kept, shown read-only as "Legacy, not enforced" |

**Legacy policies never start doing anything**, even the old drafts that said "delete after
30 days". They were written when nothing acted on them, so converting them silently would
turn a note into a deletion. Read them, and recreate the ones you still want as a schema or
lifecycle policy. Access is not a policy kind at all: who may read or write a data set comes
from [groups in your identity provider](/administration/dataset-permissions).

## Where a policy applies {#where-a-policy-applies}

The **Applies to data sets** list on a policy decides its reach:

- **No data set attached**: the policy covers the whole tenant.
- **One or more data sets attached**: it covers each of them and every data set below them in
  the hierarchy. One policy can be attached to several data sets, so "every production plant"
  is one policy, not one copy per plant.

How several policies combine depends on the kind:

| Kind | When several cover the same data |
| --- | --- |
| **Naming** | The nearest wins and replaces the ones above it |
| **Schema** | They add up: a node is held to the tenant's schema policies and those of every data set above it |
| **Lifecycle** | The nearest data set's policy wins over the ones above it and the tenant-wide one |

Two naming policies on the same data set, or two lifecycle policies there selecting the same
data, are refused when you save, so which one applies never has to be guessed.

## Naming policies, in short {#naming}

It fixes the shape of new external ids, either by preset (verbatim tags, or lowercase words
joined by underscores) or by a pattern you supply, and it runs in one of two modes:
**reject**, where the write fails and nothing is created, or **warn**, where the write
succeeds and a finding goes into a data steward's queue.

- **The nearest policy wins.** A naming policy on a data set also covers the data sets below
  it, and replaces the one above it rather than adding to it.
- **A near-duplicate guard runs regardless of the preset**, refusing `pump-a-01` next to an
  existing `pump_a_01` anywhere in the tenant.
- **It does not govern events.** An event external id is the source system's key for the
  subject the event is about, not a name anyone chose, and events are meant to share one.

[The full rules, presets and findings queue →](/concepts/naming-and-standards#naming-policies)

## Schema policies {#schema}

A schema policy is a **partial schema**: it says what matters about one kind of thing and
leaves everything else free. You choose the type it applies to (asset, time series, plain
resource, data set or function), optionally narrow it to nodes carrying certain labels, and
add rules. Each rule asks for one of:

- **a metadata key**, such as `numberOfSeats`;
- **a field**: name, description or source on anything, a location on an asset, a unit or a
  registered unit on a time series;
- **a relationship** of a given type and direction, optionally to a given type of node.

Each rule has a level:

| Level | A write that breaks it |
| --- | --- |
| **Must** | Is refused, and nothing in it is saved |
| **Should** | Is saved, and a finding goes to the findings queue showing the rule and its level |

**Example.** *Assets labelled CAR must have the metadata key `numberOfSeats`.* Creating a car
without it is refused. Creating a pump without it is fine, because the policy does not apply
to pumps.

### Existing data is judged only on what a write changes

Turning on a Must rule does not lock every old record that predates it. A write is judged only
on the rules that look at what the write changes:

- Fixing an old car's description does not demand seats, because the seats rule does not look
  at descriptions.
- Removing the seats from a car, or relabelling something as a car, is judged against the
  seats rule, and refused if it breaks it.

### The audit finds what already breaks a rule

Because old data is left alone at the write, a schema policy has an **audit**: it checks
everything the policy covers and records every broken rule as a finding, including Must rules
broken by data saved before the policy existed. It also closes findings that no longer apply,
so a fixed record leaves the queue on its own.

The audit runs **every night**, and on demand from **Run audit** on a saved schema policy,
which reports how many nodes it judged, how many broken rules it recorded and how many
findings it closed. Run it once after creating a policy to see how far your data is from it.

## Lifecycle policies {#lifecycle}

A lifecycle policy picks some data and sets one or both ages, in days:

- **Data**: datapoints, events, files and resources, any combination. For resources and
  datapoints you can narrow it further to one type and to certain labels.
- **Freeze after**: from this age, the data cannot be changed or deleted.
- **Delete after**: from this age, the nightly sweep deletes it.

Leave an age empty for never. Ages are measured on **the data's own time**: a datapoint's
timestamp, an event's time, and the moment a resource or file was created. So a backfill of
ten-year-old readings arrives already old.

**Example.** *Datapoints and events in the plant data set: freeze after 30 days, delete after
365.* Last month's readings can no longer be corrected; last year's are removed overnight.

### Freezing

A write that would change or delete frozen data is refused, with an error naming what is
frozen and which policy froze it. A few things are deliberately outside it:

- **Data sets and policies are never frozen**, so the structure and the rules stay editable.
- **Relationships stay editable**, so old equipment can still be connected to new.
- **A time series created before its datapoints' freeze age cannot be deleted**, because
  deleting it would take its frozen datapoints with it.

### Retention

Once a night the platform deletes what each lifecycle policy has kept long enough, going
through the same steps as a person's delete. What it will not do:

- **Data sets, policies and functions are never deleted.**
- **A resource still feeding a subscription, or the only link holding other nodes to the
  graph, is kept**, and counted as kept rather than forced.
- **Files go to the [trash](/using/files#deleting-and-restoring) first**, so they can be
  restored during the grace period.

Three safeguards make a mistake recoverable before it costs data:

| Safeguard | What it does |
| --- | --- |
| **Preview retention** | On a saved lifecycle policy, counts what the next sweep would delete because of it: resources, the time series whose old datapoints would go, events and files. It deletes nothing |
| **A day's grace** | A policy changed within the last day is not acted on yet, by the sweep or the preview, so a mistyped age can be corrected first |
| **A record of every sweep** | Each sweep that did something leaves an event of type `policy_retention_run`, with what it deleted and what it kept, so "what did retention remove last night?" has an answer |

Operators can also switch retention off, or make it count without deleting, for a whole
installation. [The settings →](/administration/data-lifecycle#policy-sweep-settings)

## Writing a policy worth having

The test for a good policy is the same as for a good
[description](/using/datasets#creating-one): a colleague in a year should understand not
just the rule but the reason.

<Steps>
  <Step title="Name the obligation, not just the number">
    "Delete after 10 years, [NORSOK](https://en.wikipedia.org/wiki/NORSOK_standard)
    requirement for well data" beats "delete after 10 years". The description is where the
    reason goes, and it is what lets a successor revisit the rule safely when the obligation
    changes.
  </Step>
  <Step title="Attach it to the right boundary">
    A policy follows the [data set](/using/datasets) hierarchy, so attach it as high as the
    rule is true and no higher. If a rule must cover half of a data set, narrow it by type
    and labels, or take that as a sign the boundaries need a look first.
  </Step>
  <Step title="Start with Should, then audit, then tighten">
    A new schema rule at **Should** costs nothing to try. Run the audit, work the findings
    down, and raise it to **Must** once the data meets it, so the first refusal is a surprise
    to nobody.
  </Step>
  <Step title="Preview before anything deletes">
    Save a lifecycle policy, then **Preview retention** before the next night's sweep. The
    day's grace is there so the numbers can be read before they become deletions.
  </Step>
  <Step title="Keep retention aligned with your audit horizon">
    <span className="t-accent">A reported figure can only ever be traced to inputs that
    still exist</span>, so [retention](https://en.wikipedia.org/wiki/Data_retention) on
    anything feeding a regulated report should outlive the report's auditability.
    [Retention versus traceability →](/administration/data-lifecycle#retention-versus-traceability)
  </Step>
  <Step title="Review them on a cadence">
    A quarterly pass over the policies alongside the
    [permission review](/administration/dataset-permissions#designing-a-permission-scheme),
    so the rules track reality.
  </Step>
</Steps>

## Where they appear

The **Policies** tab of the Data Governance section lists the tenant-wide policies and the
data set policies, each with its kind; legacy ones are marked "Legacy, not enforced". A
policy can be deactivated without deleting it, which keeps its findings and lets whatever it
overrode apply again. [Data sets →](/using/datasets#policies)

Warnings from naming and schema policies collect in the **Findings** tab, grouped by policy,
data set, status and either the shape of the mistake or the rule that was broken, and a
resource shows its own open findings. [The findings queue →](/concepts/naming-and-standards#findings)

Policies are one of four pieces that carry governance here, alongside the graph, data sets
and functions. [How the pieces fit →](/concepts/data-governance#how-the-pieces-carry-it)

## Where agents help

An assistant or agent can ask which rules a data set holds data to before it writes, through
the read-only `policy_list` tool: the naming convention, the schema rules for the kind of node
it is about to create, and the freeze and retention ages. Writing data that passes first time
beats being refused and guessing why. [Using MCP →](/using/mcp#the-tools-one-by-one)

A findings queue is only useful if somebody works through it. An agent can triage: group
findings that share a cause, separate the ones that need a decision from the ones that need a
correction, and draft what the correction would be.

What it must not do is close a finding on its own. The point of a finding is that a person
looked at it, and an agent that quietly resolves them has removed the control rather than
satisfied it. [Building AI agents →](/using/ai-agents)

Some rules are judgements no schema can state: whether a description says anything, whether a
data set's members still match its purpose. Those are the job for an agent given one rule.
[The policy agent →](/concepts/data-governance#the-policy-agent)
