# Files

  <Persona primary>Operations</Persona>
  <Persona primary>Engineers</Persona>
  <Persona>Document controllers</Persona>
</Personas>

<KeyIdea>
Files attach documentation to the things it documents. A
[P&ID](https://en.wikipedia.org/wiki/Piping_and_instrumentation_diagram) hangs off the line
it describes; a datasheet off the pump; an inspection photo off the vessel it was taken in.
Attached this way, documents are the
[records layer of a digital twin](/concepts/digital-twin#what-a-twin-is-made-of).

The point is not storage, you already have somewhere to put files. The point is that
<span className="hl">documentation becomes reachable from the asset</span>, instead of requiring
somebody to know which folder it was filed in.
</KeyIdea>

## What files are for here

Typical material:

- **P&IDs and network diagrams**, attached to the line, area or network segment
- **Datasheets and manuals**, attached to the equipment
- **Inspection reports and photos**, attached to the asset inspected, and datable against
  the [event](/using/events) that recorded the inspection
- **Certificates and compliance documents**, attached to the asset or the obligation
- **Calibration records**, attached to the instrument

The value is in the last word of each line. Somebody investigating a pump can reach its
datasheet from the pump. Somebody preparing a compliance submission can reach the
certificates from the obligation. Attaching a document to the thing it describes is
[contextualization](/concepts/contextualization), the same activity that links a signal to
its instrument.

## Uploading

<Steps>
  <Step title="Choose or create a folder">
    Files live in a folder tree. Create folders that mirror how people look for documents,
    usually by area or by document type, rarely by upload date.
  </Step>
  <Step title="Browse for the file and set the upload path">
    You can type the folder path directly rather than clicking through it.
  </Step>
  <Step title="Set the data set">
    Which [container](/using/datasets) it belongs to, and therefore who can see it. Do set
    one: **a file or folder left with no data set is readable by every authenticated
    user**, unlike resources, series and events.
    [Entities without a data set →](/administration/dataset-permissions#entities-without-a-data-set)
  </Step>
  <Step title="Set related resources">
    The assets this document is about. This is the field that makes the file findable from
    the model, the one worth not skipping.
  </Step>
</Steps>

Each uploaded file records a **checksum**, its **size**, its **type**, when it was created
and last modified, and the source system's own created and updated dates where those are
known. The [checksum](https://en.wikipedia.org/wiki/Checksum) is what lets you **prove a
document has not changed** since it was filed.

## Organising

| Action | What it does |
| --- | --- |
| **Rename** | Changes the file or folder name |
| **Move** | Moves it to another folder. Warns if something already exists at the destination |
| **Set dataset** | Reassigns the access boundary |
| **Set related resources** | Changes which assets the file is attached to |
| **Copy path** | Copies the full path, useful for referring to a document elsewhere |
| **Download** | Retrieves the file |
| **Update file** | Edits the entry's details: name, description, metadata, related resources, data set. File contents cannot be replaced; upload a new file |

Setting a data set on a **folder** also applies it to everything inside that does not
already have one, automatically. That is the fastest way to bring an uploaded document tree
under the right access boundary in one action, and worth knowing before you do it.

Files can also be browsed **grouped by data set**, which is the view administrators usually
want when reviewing who can see what.

## Deleting and restoring

Deleting a file moves it to a trash rather than destroying it. The **Deleted files** tab
lists what has been removed and when, and offers **Restore**.

Deleting a **folder** is different and the console says so plainly:
<span className="t-accent">it permanently deletes the folder and everything inside
it</span>, and asks you to type the folder's name to confirm. Treat that confirmation as
the safety mechanism it is.

## Looking at 3D models

A file the console recognises as a 3D model or CAD file gets a **View in 3D** button in its
file information, which opens it in a viewer you can orbit with a left drag, pan with a right
drag and zoom with the scroll wheel. The file is read in the browser exactly as it was
uploaded.

Recognised by file extension: `3dm`, `3ds`, `3mf`, `amf`, `bim`, `brep`, `dae`, `fbx`, `fcstd`,
`gltf`, `glb`, `ifc`, `iges`, `igs`, `step`, `stp`, `stl`, `obj`, `off`, `ply`, `wrl`. Plant
models in `rvm` are converted first, [see below](#plant-models-rvm).

Everything the viewer needs is served by the console itself, so this works on a closed network
with no outbound internet. The model is read in the browser, so a pump, a skid or a single
area opens comfortably. A whole plant will not.

### Sizes

When a model opens, a panel in the bottom-left corner shows its size, for example
`L 4.00 × W 0.40 × H 0.67 m` (`L × B × H` in Norwegian). Sizes are metric: millimetres while
every side is under a metre, otherwise metres with two decimals. **Click a part** to highlight
it and see its name and its own size; click empty space to go back to the whole model.

- **Height is the vertical on screen.** The viewer always shows Y as up. Length is the longer
  horizontal side, width the shorter. A model drawn with Z as up, common for STL, appears
  lying on its side and reports its depth as its height.
- **The whole model is measured along the viewer's axes; a clicked part along its own.** A pipe
  laid at an angle reads its real length and diameter.

| Format | Sizes are read in |
| --- | --- |
| glTF and GLB, VRML, COLLADA | Metres |
| STEP, IGES, BREP, FCStd, AMF | Millimetres |
| 3MF | The unit the model declares, millimetres if it declares none |
| STL, OBJ, PLY, OFF | No unit is stored, so sizes are read as metres and the panel says "This format stores no unit, so sizes assume metres" |

### Models made of several files

**Upload the whole set into the same folder as the model.** The viewer reads the model for the
files it names and fetches them from that folder: an `obj`'s `mtl` material library and the
textures that library names, and a `gltf`'s `bin` buffers and images.

- References are matched by **plain file name in the same folder**. A reference such as
  `textures/steel.png` is not found, even if that subfolder exists.
- At most **24** companion files are fetched for one model.
- Only `obj` and `gltf` files are read for references. An `fbx` or `dae` that points at
  separate texture files opens without them.
- A missing material library or texture is skipped, and the model opens grey or untextured.
  A `gltf` whose `bin` is missing does not open at all.

A self-contained file needs none of this: a `glb` with its textures inside, a `gltf` with its
data embedded, or a `3mf`.

### Plant models (RVM)

A file ending `.rvm` in any letter case, the review format plant design tools export, shows
**Convert and view in 3D** in its file information when the console is set up with a
[converter](/administration/architecture#rvm-converter-plant-models-for-the-3d-viewer).

The console looks in the same folder for an **attribute file** with the same base name, ending
`.att` or `.txt` in any letter case, and sends both to the converter. The attribute file is
optional, but upload it if you have it: without it the geometry is the same, but the parts
lose their tags, discipline, material and the rest.

The converted model opens in the viewer, which then offers **Download RVM** (the stored file)
and **Download GLB** (the converted model). The console also saves it beside the RVM as
`<name>.glb`, in the same data set, so the same people can read both and it opens next time
with plain **View in 3D**, without the converter. The saved file has source
`datahub-rvm-converter`, and metadata `convertedFrom` holding the RVM's external id. Its
external id is `<rvm external id>_glb`, or that with an extra suffix when the id is already
taken (a deleted file keeps its external id).

It never overwrites. If `<name>.glb` is already in the folder, the model is converted and shown
but nothing is saved, so delete that GLB to have the next conversion save a fresh one.

| Message | What happened |
| --- | --- |
| `Saved as <name>` | The converted model is in the folder, and the list shows it once you close the viewer |
| `<name> already exists, so the converted model was not saved` | A file of that name was in the way and was left as it is |
| `No write access to this folder, so the converted model was not saved` | You can view the model, but not add files to this folder |
| `The converted model could not be saved` | Saving failed for another reason; the model is still shown |
| `Could not convert this model` | The converter could not read the file |

## Finding files

The search box covers file names, and the filter panel narrows by folder, data set and type.
The other route, often the better one, is from the model: open a resource and see the
files related to it.

That is the difference this makes. In a conventional document store you search for the
document. Here you can <span className="hl">start from the equipment</span>, which is
usually what you actually have in front of you.

## Where agents help

Documents are the least structured thing in the platform and the most rewarding for an agent
to read. A datasheet holds the design values somebody will otherwise retype; an inspection
report holds findings that belong in the event log; a drawing holds connections that belong
in the graph.

An agent with API access can read what is attached to a piece of equipment and propose the
structured version: a [series](/using/timeseries) for a design limit, an
[event](/using/events) for a finding, a relationship for a connection. The document stays as
the source, and the model gains something queryable.
