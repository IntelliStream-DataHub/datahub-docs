# Data lifecycle

<Personas>
  <Persona primary>Administrators</Persona>
  <Persona>IT operations</Persona>
  <Persona>Finance</Persona>
</Personas>

<KeyIdea>
Storage is the dominant infrastructure cost, and it grows with ingestion whether or not
anybody reads the data.

Three levers control it: **value types** (chosen once per series, at creation),
**retention** set by lifecycle policies, and **housekeeping** that clears what is no longer
referenced.
</KeyIdea>

## Where the data actually sits

| Store | Holds | Grows with |
| --- | --- | --- |
| **Columnar store** | Measurements and events | Ingestion rate × retention. Usually the largest by far |
| **Relational database** | The model, and the system of record | Number of resources, series and data sets. Modest |
| **Graph database** | The traversable model | Number of resources and relationships. Modest |
| **File storage** | Documents and images | What people upload |

The measurements dominate everything else, typically by orders of magnitude. Cost control is
almost entirely about them.

## Lever 1 · Value types

The single most effective cost decision, and it is made once per series at creation, after
which it cannot be changed.

Choosing a 32-bit float over a 64-bit float halves the storage for that series with no
practical loss for most analogue measurements. Choosing an exact decimal type where a float
would do costs several times as much for no benefit.

Across a large estate this is not a rounding error. It is the difference between a
predictable storage bill and an alarming one.

[The full value-type guide →](/using/timeseries#value-types)

:::tip Make this a convention, not a per-user decision
Agree with your data steward which value type applies to which class of measurement, and
write it into the naming conventions document. Left to individuals, the exact-decimal types
get chosen out of caution and the bill reflects it.
[Naming and standards →](/concepts/naming-and-standards)
:::

## Lever 2 · Retention

How long data is kept. Storage for measurements is essentially
<span className="t-brand">ingestion rate × retention</span>, so this is the lever that scales
the bill linearly.

Retention is set with a [lifecycle policy](/using/policies#lifecycle): pick the data
(datapoints, events, files, resources), set **Delete after** in days, and attach it to the
data sets it governs, or to none for the whole tenant. A nightly sweep then deletes what is
older than that, on the data's own time, so a datapoint goes when its timestamp is old enough.
The same policy can **freeze** data earlier, so it can no longer be changed or deleted by
anyone. Where no lifecycle policy applies, data is kept indefinitely: plan capacity on total
ingested volume for those data sets. Retention settings on the streaming layer bound the
message log, not the stored history.

Set it per data domain rather than globally. A high-rate vibration signal used for
short-window condition monitoring and a monthly energy total used for regulated reporting
have very different useful lifetimes, and giving them the same retention means either paying
to keep the first one too long or losing the second one too early. A policy on a data set
covers the data sets below it, and the nearest one wins, so a plant-wide default with a few
exceptions is a handful of policies. "How long does it live?" is one of the five questions
[data governance](/concepts/data-governance) answers.

Two questions decide the number for any given domain:

- **How far back does anyone actually look?** Ask, rather than assuming. The answer is
  usually shorter than people expect for high-rate operational signals, and longer than they
  expect for anything feeding a report.
- **How long must it stay auditable?** See
  [retention versus traceability](#retention-versus-traceability) below, this is the one
  that catches organisations out.

### What the sweep will and will not delete

It deletes datapoints, events, files and resources past their policy's age, working through a
capped number of each per night, with the rest the next night. It never deletes data sets,
policies or functions, keeps any resource still feeding a subscription or holding the graph
together (and counts it as kept), and moves files to the trash, where
[housekeeping](#lever-3--housekeeping) purges them after the grace period. Each sweep that did
something records an event of type `policy_retention_run` with the counts, so what retention
removed can be read back later.

Before a new or changed policy deletes anything, a data steward can press **Preview
retention** on it to count what the next sweep would remove, and a policy changed within the
last day is not acted on yet, so a mistake can be corrected first.
[Retention in the policies page →](/using/policies#retention)

### Policy sweep settings {#policy-sweep-settings}

The same nightly pass also runs every schema policy's
[audit](/using/policies#the-audit-finds-what-already-breaks-a-rule). It runs inside the API
service: every instance is scheduled, and each tenant is handled by exactly one of them per
day, so adding instances does not repeat the work. These are set on the API, like its other
settings:

| Setting | Default | What it does |
| --- | --- | --- |
| `datahub.policy.sweep.enabled` | `true` | The whole nightly pass, audits and retention. `false` stops both; the console's Run audit and Preview retention still work |
| `datahub.policy.sweep.cron` | `0 15 3 * * *`, 03:15 server time | When the pass starts |
| `datahub.policy.retention.enabled` | `true` | The kill switch for deletion. `false` keeps the nightly audits and deletes nothing |
| `datahub.policy.retention.dry-run` | `false` | `true` makes the sweep count and record what it would delete, without deleting |
| `datahub.policy.retention.activation-delay` | `P1D`, one day | How long after its last change a lifecycle policy is left alone |
| `datahub.policy.retention.max-per-kind` | `10000` | How many items of each kind one night works through (events and files, per data set); the rest wait for the next night |
| `datahub.policy.audit.max-nodes` | `20000` | Nodes one audit judges at most |

:::tip Turn on retention in dry-run first
On an installation where data stewards are writing their first lifecycle policies, set
`dry-run` for a week and read the `policy_retention_run` events it records. Then switch it off
deliberately, the same way the housekeeping deletion jobs are enabled.
:::

Deleting by hand still works alongside retention. Deleting a series takes its measurements
with it, and a single time window of one series can be cleared on its own. Both complete
shortly after the request returns rather than during it, so the freed space shows up a moment
later. Neither can be undone.

## Lever 3 · Housekeeping

The platform's housekeeping service runs scheduled sweeps:

- **Soft-deleted files** are purged after a 30-day grace period, which is what makes the
  trash [restorable](/using/files#deleting-and-restoring) in the meantime
- **Stale temporary uploads** are cleared after a few days
- **Orphaned [streaming subscriptions](/using/subscriptions)** with a large backlog are
  swept, the usual cause is a durable subscriber that stopped consuming, leaving the
  platform holding its undelivered data. Note that this sweep
  ships in a report-only mode and must be deliberately enabled before it deletes anything
- **Removed tenants' folders** are quarantined for 30 days, then purged

That covers the routine accumulation that nobody would otherwise notice. The housekeeping
service now runs in the reference stack, but its deletion jobs stay in report-only mode
there: watch what they say they would remove, then enable them deliberately.
[Architecture →](/administration/architecture)

When storage grows unexpectedly and the cause is not obvious, the usual culprits are a
newly connected source ingesting at a much higher rate than expected, or a bulk file upload.
Checking recent [CDC integrations](/using/cdc-integrations) is a good first step.

## The ceiling above all three

The three levers control what a tenant **keeps**. Separately, every tenant carries a daily
ingest allowance that bounds what can **arrive** at all: bytes written a day, measurements
written a day, events and entities created a day. A second set of ceilings bounds how large a
tenant may grow in total, and those ship switched off, because they have to be reconciled
with the tenants you already have before it is safe to turn them on. Either kind can be
raised for a single tenant without a restart.
[→ Limits and quotas](/administration/limits-and-quotas)

<span className="t-accent">File storage is the gap.</span> There is no per-tenant quota on
uploaded files, so nothing refuses the upload that fills the disk. Until there is, file
volume is bounded only by capacity planning, the housekeeping sweeps above, and whatever
ceiling the storage itself has.

## Backups

Because every store is database-per-tenant, backup and restore are naturally scoped to one
tenant, and one tenant can be restored without touching the others.

For each tenant, with each store's own tools:

| Store | Backup |
| --- | --- |
| **Relational database** | A standard database dump |
| **Columnar store** | Its native backup command |
| **Graph database** | Your standard graph backup procedure |
| **File storage** | The tenant's storage root |

Two things worth deciding explicitly:

- **Consistency across stores.** The model lives in the relational database and the graph;
  the measurements live in the columnar store. A restore that takes them from different
  points in time will have a model that disagrees with its data. The simplest way to get the
  consistent point in time this asks for is a **filesystem-level snapshot across all of the
  stores on one host**, taken atomically, so that every store is captured at the same
  instant. The per-store tools above, started together from one scheduled job, are the
  fallback, and then the window between them is something to accept and document.
  [How snapshots answer this →](/administration/security#backups-and-point-in-time-recovery)
- **Retention of backups versus retention of data.** If measurements are retained for 90
  days but backups for a year, the backups are the longer record. That may be exactly what
  you want for audit purposes, or exactly what you do not want for data-minimisation
  purposes. Decide rather than discover.

### How the hosted platform does it

The hosted platform's storage is on ZFS, and its backup is the filesystem doing the work:

- **A snapshot every fifteen minutes.** Copy-on-write makes a snapshot instantaneous, and
  each one is a complete, restorable state of the stores at that instant.
- **Pulled, never pushed.** Isolated backup servers initiate every transfer by pulling the
  snapshot from production. Production holds no credential and no path to a backup, so a
  compromised production system cannot reach the copies.
- **Two copies.** Each snapshot goes to one local copy and one remote copy in another
  location.
- **Only what changed.** An incremental send ships the blocks that changed since the last
  snapshot, so the interval is set by the change rate rather than by the data size, and it
  does not lengthen as the installation grows.
- **A point in time, not a nightly.** Any snapshot can be restored, which makes the backup
  a time machine for the data rather than a copy of last night.

A self-hoster with ZFS, or with any storage that snapshots atomically across the stores'
volumes, can do the same. Without it, the per-store table above, run together and pulled
from a separate host, is the honest substitute. How long snapshots are kept, and how often
a restore is rehearsed, are decisions to make against your audit horizon and your
data-minimisation obligations rather than defaults to inherit.
[The mechanism, and why it pulls →](/administration/security#backups-and-point-in-time-recovery)

## Offboarding a tenant

Dropping the tenant's databases is the cleanest removal primitive available, there is no
residue in shared tables to hunt for, because there were no shared tables. Remove the tenant
from the registry, drop its databases, and delete its storage root. Housekeeping quarantines
removed tenants' folders for 30 days and then purges them, so an accidental offboarding has a
recovery window.

## Planning capacity

A rough approach that works:

<Steps>
  <Step title="Estimate datapoints per second, not series count">
    A thousand series at one sample per minute is a very different load from a hundred series
    at one sample per second. Only the datapoint rate matters.
  </Step>
  <Step title="Multiply by the storage per datapoint for your value types">
    This is where the value-type decision shows up in the numbers.
  </Step>
  <Step title="Multiply by retention">
    In seconds. This gives the steady-state size for measurements.
  </Step>
  <Step title="Add a generous allowance for files">
    Document uploads are lumpy and hard to predict. P&IDs and inspection photography add up
    faster than expected.
  </Step>
  <Step title="Scale ingestion capacity separately from API capacity">
    They are different services and scale independently. Ingest volume drives one; user and
    integration traffic drives the other. [Architecture →](/administration/architecture)
  </Step>
</Steps>

## Retention versus traceability

One tension worth flagging to whoever owns compliance.

[Lineage](/concepts/lineage-and-quality) lets a reported figure be traced back to the raw
measurements behind it. That only works while the raw measurements still exist. If
measurements are retained for 90 days and a figure is audited a year later, the lineage
records what the figure was computed from, but the inputs themselves are gone.

Decide deliberately which reported figures need their inputs preserved for as long as the
figure is auditable, and set retention on those data domains accordingly. It is a policy
decision, not a technical one, and it is much cheaper to make in advance.

## Where agents help

Retention is a rule that only shows up when something has already been deleted. Preview
answers what the next sweep removes; an agent can look further ahead: what is due to go next
month, what feeds a report that will outlive it, and which data sets have no retention
decision at all.

Deleting stays a human act, and everything with a grace period is designed so that it can be.
